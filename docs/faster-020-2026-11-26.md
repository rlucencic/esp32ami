# A faster 68EC020, the chips' share, 2026-11-26

TODO item 19, after `faster-020-2026-11-25.md`. That document ended with
three candidates: the hottest code in internal RAM, Deluxe Galaga's
collisions, and RISC-V with PIE. This one tries the first two, the line
records' colours (found on the way), the P4's TCM, and a count of core 1's
instructions per clock, which says whether assembly or memory placement is
the next lever.

Each build is measured on the Tab5 with step 3's harness: the six A1200
titles over 15000 frames (the median speed past frame 3000, the slowest
5 s in brackets) and the four A500 titles (core 1 over 20 s at a fixed
frame). Step 3's last build (`imm`) is the baseline.

## Step 4: the hottest code in internal RAM (not kept)

The firmware's code runs from PSRAM (`CONFIG_SPIRAM_XIP_FROM_PSRAM`)
through the 16 KB L1 instruction cache and the 256 KB L2 cache, which
chip RAM shares. The memory callbacks, Lisa's fetch, the line's end,
Paula and `m68k_execute` were already in internal RAM (`AMI_HOT`,
`M68K_FAST_FUNC`).

**What the profiles said.** A sample that lands on the first instruction
of a 64-byte line, or on a function's entry, points to a miss. With no
misses, 6.25% of samples would fall on a line's first 4 bytes.

| Title | PSRAM code: line starts, entries | Internal RAM: line starts, entries |
| --- | ---: | ---: |
| Charr | 9.6%, 5.5% | 7.2%, 1.2% |
| Christmas Breakdown | 10.0%, 6.5% | 5.3%, 1.2% |
| Deluxe Galaga | 8.8%, 3.3% | 7.6%, 1.5% |
| Gea Lux | 7.8%, 4.2% | 6.2%, 1.8% |
| Leading Lap | 9.2%, 6.6% | 8.8%, 1.3% |
| Virtual Karting 2 | 8.4%, 4.2% | 6.1%, 1.2% |

The misses cost a few points, not tens.

**The experiment.** A linker fragment (`noflash` per function, no source
change) moved the 13 KB of functions with the most samples into internal
RAM: Musashi's commonest handlers, the copper, the custom registers'
reads and writes, the collisions, the frame loop. Together they held 21%
of core 1's samples. That costs 13 KB of the internal heap, which has
~108 KB free and a low point of 26.8 KB.

| --- | ---: | ---: |
| Charr (its menu) | 94.8 (92.8) | 97.1 (94.4) |
| Christmas Breakdown | 99.8 (98.3) | 99.8 (98.9) |
| Deluxe Galaga (instructions slowest) | 81.7 (53.1) | 78.3 (54.1) |
| Gea Lux (play slowest) | 99.6 (84.8) | 99.6 (85.1) |
| Leading Lap | 78.6 (68.3) | 80.4 (69.4) |
| Virtual Karting 2 | 66.1 (61.1) | 67.2 (61.7) |

One or two points, about as much as runs vary (Deluxe Galaga's median
moves 4 points between runs of one build). Not worth 13 KB of a heap
whose low point is 27 KB.

## Step 5: Deluxe Galaga's collisions

While a title reads CLXDAT, `collide()` works out each line's collisions
(`display.c`). Deluxe Galaga reads it all the time; `matches16()` and
`collide()` took 14% of core 1 there.

**Before.** The odd/even test went over the window 16 lores pixels at a
time, and each sprite's spans did the same again. Every one of those
steps (`pf_matches()`, `matches16()`) worked the playfields' matches out
from scratch: each enabled plane's words shifted by the playfield's
scroll and matched against MVBP, two or four of them for hires and
super-hires pixels folded to lores. `win16()` built its mask a pixel at
a time. A lores window with sprites over it matched every plane 20 times
for the odd/even test alone.

**After.** `pf_line()` works out the line's matches once, for each
playfield:

- the enabled planes' words matched where they are (`d ^ inv`, ANDed);
- then moved to the window by the playfield's scroll, a word for each 16
  lores pixels from the window's start;
- a plane not fetched gives 0 all along, as before; a playfield with no
  enabled plane matches everywhere.

The odd/even test and each sprite's 16 pixels then read from those words
(`pf16()`). A sprite group whose both bits are already set is not tested
again, and a line without sprites in the window doesn't work them out.

**Checks (host).**

- A randomised check: 2 million line states (planes, fetch, scroll,
  resolution, CLXCON and CLXCON2, sprites in every width and SPRES) give
  the old code's CLXDAT. It catches each of three bugs planted to test it.
- A checking build runs the old code beside the new on every line where
  collisions are worked out, over the 96-game collection: no difference.
  It caught a name clash in a draft (X-Balls, Deluxe Galaga) before it went
  anywhere.
- `tools/agaboot.py`'s clx7, clx7off, clx7reset, clxwide and clxwide0
  pass.
- The collection's pictures, 96 of 96 the same.

**On the Tab5:** see the table after step 7. In the profiles of Deluxe
Galaga's slow stretch, the collisions took 11-15% of core 1 before
(`collide`, `matches16`, `pf_matches`) and 5-6% after (`collide`,
`pf_line`).

## Step 6: the line records' colours

Each line record holds the palette as the line began: 32 colours on OCS
and ECS, 256 on AGA (1 KB). When a record's key changed, the whole
palette was copied in with it, even though almost every line has the same
palette as the one before. Counted on the host over 6000 frames:

| Title | Records written | Colours copied | Planes copied |
| --- | ---: | ---: | ---: |
| Charr | 459146 | 459 MB | 93 MB |
| Leading Lap | 419902 | 420 MB | 113 MB |
| Virtual Karting 2 | 474885 | 475 MB | 209 MB |
| Christmas Breakdown | 95191 | 95 MB | 20 MB |

The colours were 70-83% of what the records copied: that is most of
`memcpy`'s 7-13% of core 1.

**Now** a record points to its palette (`row_t.pal`). It points to the
copy in an earlier record of the same frame when the palette's hash is the
same; else it copies the palette into its own record (only if that record
doesn't already hold it) and becomes the one the next lines point to. The
key still includes the palette's hash, so the presenter's cache sees the
same changes as before.

The last row of a 313-line frame isn't written by a 312-line one
(interlace's short frames). A pointer there would be left pointing at a
row that the next frame changes. So rows past the standard's shorter frame
(`s.sure_rows`) always hold their own copy. The first version missed this,
and Fatman's last line differed.

**Checks (host).**

- The collection's pictures, 96 of 96 the same.
- Every shot of `tools/laceboot.py` (PAL, NTSC, the A1200),
  `tools/shresboot.py` and `tools/agaboot.py` the same.

## Step 7: the TCM

The P4 has 8 KB of TCM (`SPM_IRAM_ATTR`): no wait states, no cache, and
outside the heap. The hottest 7.9 KB of the code already in internal RAM
went there: `m68k_execute`, the fetch (`m68k_read_immediate_16`,
`prefetch16`), the memory callbacks for 16 and 32 bits, `display_fetch`,
`display_line_end` and `audio_line`.

It made everything much slower: X-Balls on the A500 fell to 82-84% speed
with core 1 at 100%, and the A1200 titles lost 25-40% (table below). Code
run from the TCM is evidently far slower here than code that hits in the
L1 cache. Why wasn't looked into; it is not kept.

## Step 8: instructions per clock

A measuring build (not kept) read the P4's `mcycle` and `minstret` around
each `run_frame` on core 1, and the console's `i` printed the ratio since
the last `i`. Over each run past frame 3000:

| Title | Instructions a clock | In its slowest stretch |
| --- | ---: | ---: |
| Charr | 0.64 | 0.64 |
| Christmas Breakdown | 0.66 | 0.67 |
| Deluxe Galaga | 0.62 | 0.65 |
| Gea Lux | 0.78 | 0.78 |
| Leading Lap | 0.63 | 0.62 |
| Virtual Karting 2 | 0.68 | 0.67 |

The ratio is about the same in the slow stretches as anywhere else. Where
the code lives barely changes the speed (steps 4 and 7), so the misses
aren't what is left. The stalls that remain come with the instructions:
the dispatch's indirect jump to a handler for every 68020 instruction,
data from PSRAM. Fewer P4 instructions per 68020 instruction is the
lever, and fewer of those jumps with it. That is assembly for the fetch
and the dispatch.
