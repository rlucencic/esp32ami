## Step 1: short loops without the CPU

`wait.c`'s decoder took a test and a Bcc. It now takes a loop of up to
16 instructions that ends in a branch back to its first:

- moves into data or address registers, MOVEQ;
- pushes and pops on the stack (MOVE to -(A7), from (A7)+, MOVEM.L);
- EXT, SWAP, AND, OR, ASR/LSR/LSL #n;
- TST, CMP, CMPI, BTST, Scc;
- forward branches (inside the loop, or out of it), NOP.

Operands: Dn, An, (An), (d16,An), abs.W, abs.L, (d16,PC), #imm. Anything
else (a write to memory, an indexed operand, a loop inside) and the PC is
in no loop.

**One pass, worked out.** From the registers and memory as they are, with
`mem_peek()`'s side-effect-free reads, the evaluator runs one pass:

- Values carry their **unstable bits**. VHPOSR's horizontal byte changes
  within a slice, alone, in the word, or in the VPOSR+VHPOSR long that
  `mem_peek()` now reads. AND, OR and the shifts carry the marks along.
  A branch or Scc that rests on an unstable bit ends the attempt. The
  beam wait's `andi.l #$1ff00` removes them; a compare that needs the
  horizontal position doesn't skip.
- Pushes go to a small stack of the pass's own. A pop takes them back,
  and a write above the stack pointer must equal memory.
- The pass must come back to the loop's start with the registers and
  flags it started with: **a fixed point**. Then every pass to the
  slice's end would be the same, and the slice passes without the CPU
  (no interrupt due, no trace bit, as before).

**Committing the pass.** A beam wait is never a fixed point as a line
begins: its register still holds the line before's position. So the
evaluator allows one more pass. If the state after the first pass is a
fixed point, the CPU is set to it and to the loop's start. That is the
pass the CPU would run next with memory as it is. Without the commit, the
skip would leave the stale register, and code after the loop would read
it (the test `register_after_wait` read line 1 instead of 312 or 0).

**ICR.** Reading a CIA's ICR clears its flags. A loop polling ICR for
timer A takes any other flag (the index, timer B) with its next read, and
code after the loop must not find it still set. `cia_peek()` now refuses
ICR while a flag is pending: the CPU runs that read, and the next check can
skip again.

### Hyperion: a coin toss on timing, before and after

With this build Hyperion's loader seeks without end at frame 2339.

- Its track read of cylinder 37, side 1, starts right after sector 0's
  second sync word, at the sector's header. Sector 0 then has no sync in
  the 6656-word buffer, its second copy at the end is cut off, and the
  loader steps forever.
- That happens when DSKLEN is written within a sector's second sync word,
  a 32 µs window. A real Paula has the same window.
- The loader starts each read 15 ms after the last one's work, so the
  phase at which DSKLEN lands drifts deterministically from read to read.
  Whether one of its ~130 reads hits the window depends on clock-level
  timing.
- With a key tapped at frame 208, item 18's build fails the same way and
  this one passes. Taps at frames 200-205 change neither.

So it isn't the skip, but the collection will keep flipping on it. TODO
item 21.

## Step 2: a cheaper fetch

In the titles that compute, each 68020 instruction costs about 1 µs of
core 1, around 150 P4 instructions with the chipset's share. The profiles'
samples spread evenly over the code, so the cost is the instruction count.
In Virtual Karting 2, Leading Lap, Tactical Manager 2, Gea Lux and AmiBee:

| Part | Share of core 1 |
| --- | ---: |
| The instruction fetch (`m68k_read_immediate_16`, Musashi's `m68ki_read_imm_*`) | 22-35% |
| Musashi's dispatch loop (`m68k_execute`, ~45 P4 instructions an instruction) | 13-23% |
| The instruction handlers | 9-21% |
| Data memory | 5-23% |

Two things that weren't levers:

- This P4 is revision 1.x: 360 MHz is its top clock.
- A 512 KB L2 cache instead of 256 KB would need 256 KB of internal RAM;
  about 110 KB is free (40 KB at its low point).

**The change** (`mem.c`, nothing shared):

- `s_ic.next` even means the pointer to the next word is valid, so one
  compare replaces three (the address, the pointer, the bank's end).
- Only a longword's second word checks for a bank's end (`a + 2 << 16`),
  and only a first word looks at the cache.
- The state is in `.sdata` (`AMI_SDATA`), reached from `gp`: no address
  to build.
- `m68k_read_immediate_32` is two 16-bit fetches.

| Word | P4 instructions before | After |
| --- | ---: | ---: |
| A longword's second word | 19 | 17 |
| A first word in the cache | 28 | 25 |

The rare cases count a little differently: a word from the slow path, and
the first word after a map change, count as a longword's first word. No
code runs in the slow path's banks. The host collection against step 1's
build: 96 of 96 the same.

## What is left

The titles still behind compute: Deluxe Galaga's instructions and Game
Control screens (~50%), Virtual Karting 2's race (~60%), Leading Lap
(~70%), Gea Lux in play (~77%), AmiBee's 5000-7000 (~68%), Charr's menu
(85%). They need roughly 1.3 to 2 times the speed. The fetch and the
dispatch together are still 35-50% of core 1, so the next candidates are:

- **Musashi's prefetch around each fetch** (about 10 P4 instructions a
  word: the compare with `CPU_PREF_ADDR`, the stores). The 68000 needs it
  (Voyage); the 68EC020 doesn't.
- **The dispatch loop's per-instruction work**: the trace flag's store
  and test, the debugger's map, the cycle table's lookup.
- **The handlers run from flash through the cache** (their addresses are
  $480xxxxx, not IRAM): the hottest few in IRAM, if internal RAM allows.

All three are in esp32emu's Musashi, shared with the ST and the Macs:
each needs those built and checked too. Then RISC-V with PIE.
